You might assume BigQuery Graph is only for fraud rings, social networks, or supply-chain traversals where your data already looks like a graph. In this post, we use it for something much more everyday: building a shared semantic layer inside BigQuery over ordinary relational tables. Tables become nodes, foreign keys become edges, and BigQuery measures1 attach grain-locked metrics to each entity.

One BigQuery Graph holds:

  • Join paths across your relational tables, without copying rows
  • Measures: reusable, grain-aware metrics (sums, conditional counts, and weighted ratios) that stay accurate when you join or filter across tables at different grains

SQL, Data Studio, Knowledge Catalog, and AI agents then read the same contract instead of duplicating logic across views, dashboards, and prompts.

BigQuery graphs can be queried just like regular tables, so you can try the examples below in a BigQuery project yourself (all SQL scripts live in edemir/bq-graph-knowledge).

Self-documenting graph#

Before looking at the DDL, three design choices explain how BigQuery Graph works as a semantic layer over relational tables.

Logical construct#

A BigQuery property graph is a logical schema object, not a second database. CREATE PROPERTY GRAPH stores metadata that maps existing BigQuery storage into nodes and edges at query time. It sits directly over standard tables, BigLake Iceberg tables, external tables, or views (including authorized views).

flowchart LR
    C["SQL · Data Studio · Catalog · Agents"]
    G["demo.CommerceGraph<br/>logical metadata only"]
    S["Existing storage<br/>Tables · Iceberg · Views"]

    C --> G
    G -. "maps at query time<br/>(zero copy)" .-> S

No rows are copied and no sync pipeline runs in the background. When a new row lands in demo.orders, the next graph query sees it immediately. Partitioning, clustering, row-level security, and column masking stay on the underlying tables. Physical column descriptions and value profiles still belong on the base tables and in Knowledge Catalog, while the graph DDL documents the semantic contract (entities, relationships, measures, synonyms, and metric owners).

Semantic edges#

Foreign keys on demo.orders and demo.order_items tell BigQuery which columns match, not what the business relationship means. Graph edges turn those joins into named, directed connections (LineOf, PlacedBy, OpenedBy). You do not need separate junction tables for N:1 relationships; demo.order_items acts as both the OrderItem node and the LineOf edge through table aliases:

demo.order_items AS LineOf
  SOURCE KEY (item_id) REFERENCES OrderItem (item_id)
  DESTINATION KEY (order_id) REFERENCES Orders (order_id)
  DEFAULT LABEL OPTIONS (
    description = 'Connects each order line item to its parent order (N:1)',
    synonyms = ['belongs to order', 'part of order'],
    extensions = [('cardinality', 'N:1')]
  )
  NO PROPERTIES

Because the base tables already declare primary keys, BigQuery infers each node and edge KEY automatically. DEFAULT LABEL OPTIONS (...) documents the relationship itself (description, synonyms, and extensions).

Grain-locked measures#

SQL views compute aggregates at query time, which breaks as soon as a downstream join multiplies rows. In BigQuery Graph, MEASURE(...) attaches each aggregation directly to its owning node’s key alongside its description, synonyms, and extensions:

  • Orders (order_id): order-level revenue, shipping, order count, refund rate, and paying customer count
  • OrderItem (item_id): line-item sales revenue
  • SupportTicket (ticket_id): ticket count and total resolution hours

For example, on Orders, a conditional sum (refunded_revenue) feeds a derived ratio (refund_rate_pct) via AGG(...):

MEASURE(SUM(order_total)) AS gross_revenue,
MEASURE(
  SUM(CASE WHEN status = 'refunded' THEN order_total ELSE 0.0 END)
) AS refunded_revenue,
MEASURE(
  SAFE_DIVIDE(AGG(refunded_revenue), NULLIF(AGG(gross_revenue), 0)) * 100.0
) AS refund_rate_pct

When a query evaluates AGG(Orders_refund_rate_pct) after joining Orders with OrderItem, BigQuery deduplicates each order_id once before running the CASE WHEN and SUM aggregations, and only then divides the two totals. Multiplying Ord-001 across three line items cannot inflate gross_revenue or skew the refund percentage.

Putting all four nodes, three edges, and nine measures together gives the full graph:

-- sql/02_commerce_graph.sql (https://github.com/edemir/bq-graph-knowledge/blob/main/sql/02_commerce_graph.sql)
CREATE OR REPLACE PROPERTY GRAPH demo.CommerceGraph
  NODE TABLES (
    demo.customers AS Customer
      DEFAULT LABEL OPTIONS (
        description = 'Customer accounts across Enterprise and SMB segments',
        synonyms = ['account', 'client']
      )
      PROPERTIES (customer_id, customer_name, segment),

    demo.orders AS Orders
      DEFAULT LABEL OPTIONS (
        description = 'Customer purchase orders at one row per order',
        synonyms = ['purchase', 'transaction']
      )
      PROPERTIES (
        -- Columns referenced by MEASURE(...) must stay in PROPERTIES(...);
        -- row-level order_total and shipping_fee also remain available for WHERE filters and GQL MATCH.
        order_id, customer_id, status, order_total, shipping_fee,
        MEASURE(SUM(order_total)) AS gross_revenue OPTIONS (
          description = 'Gross order value in USD before refunds',
          synonyms = ['GMV', 'gross_sales'],
          extensions = [('unit', 'USD'), ('owner', 'finance-analytics'), ('reporting_tier', 'executive')]
        ),
        MEASURE(COUNT(order_id)) AS order_count OPTIONS (
          description = 'Total unique order count',
          synonyms = ['number of orders', 'orders'],
          extensions = [('owner', 'revops')]
        ),
        MEASURE(SUM(shipping_fee)) AS total_shipping OPTIONS (
          description = 'Order-level shipping fee in USD',
          synonyms = ['shipping cost', 'shipping'],
          extensions = [('unit', 'USD'), ('owner', 'logistics-ops')]
        ),
        MEASURE(SUM(CASE WHEN status = 'refunded' THEN order_total ELSE 0.0 END)) AS refunded_revenue OPTIONS (
          description = 'Total USD value of refunded orders',
          extensions = [('unit', 'USD'), ('owner', 'finance-analytics')]
        ),
        MEASURE(
          SAFE_DIVIDE(AGG(refunded_revenue), NULLIF(AGG(gross_revenue), 0)) * 100.0
        ) AS refund_rate_pct OPTIONS (
          description = 'Dollar-weighted refund rate percentage',
          synonyms = ['return rate', 'refund %'],
          extensions = [('unit', 'percent'), ('owner', 'finance-analytics'), ('reporting_tier', 'executive')]
        ),
        MEASURE(
          COUNT(DISTINCT CASE WHEN status = 'completed' THEN customer_id END)
        ) AS completed_buyer_count OPTIONS (
          description = 'Distinct paying customer count (completed orders only; excludes refunded orders)',
          synonyms = ['active buyers', 'paying customers'],
          extensions = [('owner', 'growth-analytics')]
        )
      ),

    demo.order_items AS OrderItem
      DEFAULT LABEL OPTIONS (
        description = 'Individual product line items within an order',
        synonyms = ['line item', 'order line']
      )
      PROPERTIES (
        item_id, order_id, category, unit_price, qty,
        MEASURE(SUM(unit_price * qty)) AS item_sales OPTIONS (
          description = 'Line-item sales revenue (unit_price * qty)',
          synonyms = ['category sales', 'product sales'],
          extensions = [('unit', 'USD'), ('owner', 'merchandising')]
        )
      ),

    demo.support_tickets AS SupportTicket
      DEFAULT LABEL OPTIONS (
        description = 'Customer support tickets with topic and resolution time',
        synonyms = ['case', 'helpdesk ticket']
      )
      PROPERTIES (
        ticket_id, customer_id, topic, resolution_hours,
        MEASURE(COUNT(ticket_id)) AS ticket_count OPTIONS (
          description = 'Total unique support tickets',
          synonyms = ['support tickets', 'tickets'],
          extensions = [('owner', 'support-ops')]
        ),
        MEASURE(SUM(resolution_hours)) AS total_resolution_hours OPTIONS (
          description = 'Total support resolution hours',
          synonyms = ['resolution hours', 'support hours'],
          extensions = [('unit', 'hours'), ('owner', 'support-ops')]
        )
      )
  )
  EDGE TABLES (
    demo.order_items AS LineOf
      SOURCE KEY (item_id) REFERENCES OrderItem (item_id)
      DESTINATION KEY (order_id) REFERENCES Orders (order_id)
      DEFAULT LABEL OPTIONS (
        description = 'Connects each order line item to its parent order (N:1)',
        synonyms = ['belongs to order', 'part of order'],
        extensions = [('cardinality', 'N:1')]
      )
      NO PROPERTIES,
    demo.orders AS PlacedBy
      SOURCE KEY (order_id) REFERENCES Orders (order_id)
      DESTINATION KEY (customer_id) REFERENCES Customer (customer_id)
      DEFAULT LABEL OPTIONS (
        description = 'Connects each order to the customer who placed it (N:1)',
        synonyms = ['ordered by', 'bought by'],
        extensions = [('cardinality', 'N:1')]
      )
      NO PROPERTIES,
    demo.support_tickets AS OpenedBy
      SOURCE KEY (ticket_id) REFERENCES SupportTicket (ticket_id)
      DESTINATION KEY (customer_id) REFERENCES Customer (customer_id)
      DEFAULT LABEL OPTIONS (
        description = 'Connects each support ticket to the customer who opened it (N:1)',
        synonyms = ['filed by', 'submitted by'],
        extensions = [('cardinality', 'N:1')]
      )
      NO PROPERTIES
  );

This single DDL encodes all six GA measure forms: simple aggregates (SUM), expressions inside aggregates (unit_price * qty), conditional aggregates (CASE WHEN), conditional distinct counts (COUNT(DISTINCT CASE WHEN ...)), derived AGG() ratios validated at compile time, and scalar operations outside aggregates (* 100.0).

GRAPH_EXPAND traverses in the N:1 direction inferred from table keys and calls each fact table with no incoming N:1 edges a root node. Because CommerceGraph has two root nodes (OrderItem and SupportTicket), start_node is required to pick which branch to expand: pick the finest-grained node you need to filter or group by. Here we filter on OrderItem_category = 'Accessory', so start_node => 'OrderItem' walks OrderItem -> Orders -> Customer with grain-locked deduplication (for order-only metrics without line-item filters, you would pass start_node => 'Orders'):

-- sql/03_queries.sql (https://github.com/edemir/bq-graph-knowledge/blob/main/sql/03_queries.sql)
SELECT
  Customer_segment,
  AGG(OrderItem_item_sales) AS item_sales,
  AGG(Orders_gross_revenue) AS basket_value,
  AGG(Orders_total_shipping) AS order_shipping,
  AGG(Orders_refund_rate_pct) AS refund_rate_pct
FROM GRAPH_EXPAND('demo.CommerceGraph', start_node => 'OrderItem')
WHERE OrderItem_category = 'Accessory'
GROUP BY Customer_segment;

Measures prevent three common SQL view bugs here:

  1. No dropped shipping: order_shipping stays $30.0. A ROW_NUMBER() = 1 view that pins shipping to the first line item (Item-001, Hardware) drops it and returns $0 once you filter WHERE category = 'Accessory'.
  2. Accurate weighted ratios: Removing the WHERE filter rolls refund_rate_pct up to the dollar-weighted 10.0% ($100 / $1,000) for Enterprise instead of 50.0% from AVG() over an order-grain view.
  3. Compile-time type safety: Writing SUM(Orders_gross_revenue) fails before scanning a single byte because BigQuery allows MEASURE columns only inside AGG().

When a question spans two fact branches (Orders and SupportTicket), start_node isolates each branch on the same graph:

SELECT
  COALESCE(EO.Customer_segment, ET.Customer_segment) AS segment,
  AGG(EO.Orders_gross_revenue) AS gross_revenue,
  AGG(EO.Orders_refund_rate_pct) AS refund_rate_pct,
  AGG(EO.Orders_completed_buyer_count) AS completed_buyers,
  AGG(ET.SupportTicket_ticket_count) AS ticket_count,
  AGG(ET.SupportTicket_total_resolution_hours) AS resolution_hours
FROM GRAPH_EXPAND('demo.CommerceGraph', start_node => 'Orders') AS EO
FULL OUTER JOIN GRAPH_EXPAND('demo.CommerceGraph', start_node => 'SupportTicket') AS ET
  ON EO.Customer_customer_id = ET.Customer_customer_id
GROUP BY segment
ORDER BY segment;

Each branch keeps its native grain across Cust-001, while FULL OUTER JOIN retains zero-order customer Cust-002’s Enterprise ticket (Tkt-003). On large tables, pre-aggregate each start_node branch in a CTE before joining to avoid an M x N shuffle.

Root-cause traversal#

Once GRAPH_EXPAND surfaces Enterprise’s 10.0% refund rate, the exact same graph traces which customer and tickets sit behind it using ISO GQL:

GRAPH demo.CommerceGraph
MATCH (o:Orders {status: 'refunded'})-[:PlacedBy]->(c:Customer {segment: 'Enterprise'})<-[:OpenedBy]-(t:SupportTicket)
RETURN c.customer_name, o.order_id, o.order_total, t.topic, t.resolution_hours

Syntax boundaries#

Syntax boundaries across MEASURE(...), AGG(...), and GQL MATCH:

SurfaceAllowedDisallowed
MEASURE(...) DDLSUM, AVG, MIN, MAX, COUNT(col), COUNT(DISTINCT ...), CASE WHEN, arithmetic, derived AGG() ratiosCOUNT(*)/COUNT(1), COUNTIF, APPROX_COUNT_DISTINCT, WHERE modifiers, subqueries, OVER windows
AGG(...) queriesGROUP BY, HAVING AGG(...), ORDER BY AGG(...), SAFE_DIVIDE(AGG(...), AGG(...)), outer windows wrapping AGG() (such as SUM(AGG(...)) OVER ())AGG(... WHERE ...), AGG(DISTINCT ...), direct AGG(...) OVER (), GROUP BY ROLLUP/CUBE/GROUPING SETS
GQL MATCHNon-measure node and edge properties (o.order_total, c.segment, t.topic)Direct reads of MEASURE properties (query via GRAPH_EXPAND + AGG() instead)2

Allowed MEASURE(...) expressions inside a node’s PROPERTIES(...) list cover standard aggregates, conditional counts, and derived ratios:

-- Allowed MEASURE(...) patterns inside CREATE PROPERTY GRAPH ... PROPERTIES (...)
MEASURE(AVG(order_total)) AS avg_order_value,
MEASURE(MIN(order_total)) AS min_order_value,
MEASURE(MAX(order_total)) AS max_order_value,
MEASURE(COUNT(DISTINCT CASE WHEN status = 'completed' THEN customer_id END)) AS completed_buyer_count,
MEASURE(SAFE_DIVIDE(AGG(refunded_revenue), NULLIF(AGG(gross_revenue), 0)) * 100.0) AS refund_rate_pct

On the query side, AGG(...) supports outer ratios, window functions wrapping AGG(...) for share-of-total, HAVING, and ORDER BY in one query (Enterprise: $1,000.0 GMV, 10.0% refund, 83.3% share; SMB: $200.0 GMV, 0.0% refund, 16.7% share):

SELECT
  Customer_segment,
  AGG(Orders_gross_revenue) AS gmv,
  ROUND(SAFE_DIVIDE(AGG(Orders_refunded_revenue), AGG(Orders_gross_revenue)) * 100, 1) AS refund_pct,
  ROUND(SAFE_DIVIDE(AGG(Orders_gross_revenue), SUM(AGG(Orders_gross_revenue)) OVER ()) * 100, 1) AS gmv_share_pct
FROM GRAPH_EXPAND('demo.CommerceGraph', start_node => 'Orders')
GROUP BY Customer_segment
HAVING AGG(Orders_gross_revenue) >= 200
ORDER BY AGG(Orders_gross_revenue) DESC;

Tradeoffs#

BigQuery Semantic Graph complements existing layers rather than replacing them:

LayerBest fitHow it fits with BigQuery Graph
Regular SQL viewsSingle-grain projections, row-level security, column masking, staging ETLFeed clean tables or views into NODE TABLES
LookMLBI semantic modeling and Git-driven Explore authoringCompiles Explores and base measures into BigQuery Graph via derived analytic models so SQL, notebooks, Data Studio, and AI agents share one definition
dbt MetricFlowdbt-centric transformation and metric workflowsFederates metadata into Knowledge Catalog for unified discovery

Four operational boundaries are worth planning around:

  1. Raw columns stay visible in SQL: GA DDL requires columns referenced in MEASURE(...) to appear in PROPERTIES(...), so Orders_order_total stays visible alongside Orders_gross_revenue.
  2. Full-graph replacement and unique aliases: CREATE OR REPLACE PROPERTY GRAPH replaces the entire graph (manage it in Git or Dataform), and MEASURE aliases must be unique graph-wide.
  3. Explicit multi-fact joins and single-element ratios: Separate start_node branches still join in SQL, and cross-node ratios are computed in outer SQL.
  4. Cache and billing: GRAPH_EXPAND query cache does not auto-invalidate on graph DDL changes, and on-demand GRAPH_EXPAND and MATCH queries bill by bytes scanned on the base tables.

Regular SQL views remain the right tool for projections, access control, and ETL staging. When metrics, owners, synonyms, and entity relationships need to live in one self-documenting contract, BigQuery Graph puts that semantic layer directly inside the query engine.
