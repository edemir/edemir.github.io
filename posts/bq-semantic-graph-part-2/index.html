Grounding an ADK 2 Agent on BigQuery Semantic Graphs

In Part 1, we defined CommerceGraph over four ordinary relational tables so SQL, Data Studio, and Knowledge Catalog share one grain-locked semantic contract.

When your semantic layer documents itself in Knowledge Catalog, you only need a compact portable skill and gemini-4-hydrogen at LOW thinking on Google ADK 2 to build a governed analytics agent. In this post, we wire those pieces together and test them across 20 business and adversarial questions. All companion SQL, agent code, and skill files live in edemir/bq-graph-knowledge under part2_skill/.

One query end to end#

Before unpacking the wiring, here is what happens when you ask the live agent a classic line-item fanout trap (“For orders that included Hardware, what was the total gross order value, the refunded order value, and the dollar refund rate percentage?”). Joining orders directly to order_items inflates order_total by ~200%. On Turn 1, gemini-4-hydrogen (LOW thinking) loads bigquery-semantic-graph, writes one 6-line GRAPH_EXPAND query with zero joins and zero CTEs, and returns the exact answer in 8.7s:

SELECT
  AGG(Orders_gross_revenue) AS total_gross_order_value,
  AGG(Orders_refunded_revenue) AS refunded_order_value,
  AGG(Orders_refund_rate_pct) AS dollar_refund_rate_pct
FROM GRAPH_EXPAND('my-project.commerce_bench.CommerceGraph', start_node => 'OrderItem')
WHERE OrderItem_category = 'Hardware';
MetricValue
Total Gross Order Value$565,804
Refunded Order Value$64,088
Dollar Refund Rate11.33%

Without any schema-specific few-shot examples, the agent filtered at the OrderItem grain (OrderItem_category = 'Hardware'), called the governed parent-grain Orders measures directly (AGG(Orders_gross_revenue), AGG(Orders_refunded_revenue), and the derived ratio AGG(Orders_refund_rate_pct)), and let BigQuery deduplicate the order totals automatically. The rest of this post walks through how that works.

The setup#

To test whether a portable skill can teach BigQuery Graph syntax from scratch, we used gemini-4-hydrogen (LOW thinking), whose training knowledge does not include BigQuery’s new GRAPH_EXPAND and property graph MEASURE capabilities. Any valid graph query has to come from the skill and Knowledge Catalog context at runtime rather than pretraining.

We also scaled the 14-row toy dataset from Part 1 up to a 3,018-row benchmark (commerce_bench): 120 customers (including 18 zero-order accounts), 640 orders, 1,918 order items, and 340 support tickets. At this scale, naive SELECT * peeks fail to fit in context, and unguarded multi-table joins produce severe fanout: joining orders to order_items inflates order totals and shipping fees by ~200%, joining orders and support_tickets through customers inflates order totals by ~390% and ticket resolution hours by ~590%, and joining all three child tables inflates totals by ~1,250% to ~1,960% globally (and up to ~4,000% on individual high-activity accounts).

We tested the live agent against a 20-question benchmark (BENCHMARK_QUERIES.md). Ten questions cover multi-grain business metrics (B01 through B10), and ten test adversarial traps (T01 through T10): line-item fanout, joining two independent child tables (orders and support_tickets) through the same customer, zero-denominator ratios, partial-scope filters, and missing time axes. The agent sees only its project and dataset env vars, Knowledge Catalog metadata, and a read-only SQL execution tool.

Architecture#

The entire agent codebase stays around 250 lines by hydrating Knowledge Catalog metadata once in an async ADK callback, scoping SQL tool exposure to an active SkillToolset skill, and running queries through ADK’s built-in BigQueryToolset:

flowchart LR
    KC["[CATALOG] Knowledge Catalog<br/>searchEntries + lookupContext"] -->|"1-hop YAML (TTL cached)"| A["[RUNTIME] ADK 2 Agent<br/>App + session state"]
    A -->|"load_skill activates execute_sql"| S["[SKILL] SkillToolset<br/>EAGER frontmatter + BigQueryToolset"]
    S -->|"WriteMode.BLOCKED"| BQ["[QUERY] BigQuery<br/>GRAPH_EXPAND + ISO GQL"]

Knowledge Catalog links metadata in a three-step chain (Graph <-> Graph Node <-> Base Table), and :lookupContext traverses 1 hop in both directions. Querying :searchEntries for bigquery-graph-node entries and passing those node resource names into one :lookupContext call returns graph topology, MEASURE definitions, synonyms, and base-table Dataplex Data Profiles (sampleValues) in a single YAML payload without scanning any BigQuery tables (full implementation in agent.py):

function fetch_graph_context(project, dataset, location):
  nodes = dataplex.searchEntries(
    scope = project,
    query = "name:{dataset}/propertyGraphs/",
    filter = entryType ends with "/bigquery-graph-node"
  )
  yaml_ctx = dataplex.lookupContext(location, resources = nodes)
  return strip_field(yaml_ctx, "sampleQueries")

We strip sampleQueries before injecting the YAML into the prompt because Knowledge Catalog’s :lookupContext includes historical SQL examples written against the raw base tables (customers, orders, order_items, support_tickets), which both bloat the context and tempt the model to bypass CommerceGraph instead of using GRAPH_EXPAND.

Progressive skill gating#

Prompting a model to load a skill before writing SQL works most of the time, until it does not. In ADK 2 (google-adk==2.14.1), adk_additional_tools lets a skill declare extra tools that SkillToolset only exposes to the model while that skill is active (and hides again if the skill is unloaded).

By listing execute_sql under metadata.adk_additional_tools in the skill frontmatter and passing BigQueryToolset into SkillToolset(additional_tools=[...]) instead of attaching it directly to the agent, execute_sql stays hidden until load_skill activates bigquery-semantic-graph:

# part2_skill/agent_under_test/agent.py (ADK 2 wiring)
root_agent = Agent(
    name="bq_semantic_graph_analyst",
    model=Gemini(
        model=MODEL_ID,  # gemini-4-hydrogen
        client_kwargs={"vertexai": True, "project": PROJECT_ID, "location": "global"},
    ),
    description=(
        "Answers analytics questions over BigQuery Property Graphs using "
        "Knowledge Catalog metadata and governed measures."
    ),
    generate_content_config=types.GenerateContentConfig(
        thinking_config=types.ThinkingConfig(thinking_level=THINKING_LEVEL),  # LOW
    ),
    before_agent_callback=_ensure_graph_context,
    before_tool_callback=_cap_dry_runs,
    instruction=(
        f"You are a data analytics assistant for BigQuery dataset `{BQ_PROJECT_ID}.{DATASET}` "
        f"(location `{LOCATION}`). Answer accurately using governed data and never guess numbers. "
        "`execute_sql` already enforces read-only mode and a 1 GB scan cap automatically; "
        "run your composed query directly (`dry_run=False`) instead of dry-running individual CTEs.\n\n"
        "```yaml\n{graph_context?}\n```"
    ),
    tools=[
        SkillToolset(
            skills=load_skills_from_dir(SKILLS_DIR),
            discovery_mode=SkillDiscoveryMode.EAGER,
            # Keep execute_sql in tool_filter so SkillToolset exposes it once load_skill runs.
            tool_filter=["load_skill", "execute_sql"],
            additional_tools=[
                BigQueryToolset(
                    tool_filter=["execute_sql"],
                    bigquery_tool_config=BigQueryToolConfig(
                        write_mode=WriteMode.BLOCKED,
                        compute_project_id=BQ_PROJECT_ID,
                        default_project_id=BQ_PROJECT_ID,
                        location=LOCATION,
                        max_query_result_rows=200,
                        maximum_bytes_billed=1_073_741_824,
                    ),
                ),
            ],
        ),
    ],
)

app = App(name="agent_under_test", root_agent=root_agent)

Before load_skill runs on Turn 1, SkillToolset.get_tools() exposes only ['load_skill']. Calling execute_sql before reading the skill is impossible, and zero-SQL abstention questions skip the SQL tool schema entirely. Once load_skill activates bigquery-semantic-graph, ADK’s persistent lifecycle appends execute_sql in insertion order for the rest of the session so Gemini’s prefix cache stays intact across follow-up turns. Because WriteMode.BLOCKED already executes an internal BigQuery dry run automatically before running any query, the instruction and _cap_dry_runs callback stop the model from wasting extra round-trips on manual dry_run=True checks.

Symbolic skill design#

To avoid overfitting the skill to a specific domain schema, we write all examples with pure topological symbols (Entity, Parent, Child, BranchA, BranchB, m1, m2, m3, cnt) and keep the file to 79 lines (~5 KB) with zero schema coupling (SKILL.md):

---
name: bigquery-semantic-graph
metadata:
  version: "0.9.5"
  category: BigDataAndAnalytics
  adk_additional_tools:
    - execute_sql
description: >-
  Queries BigQuery Property Graphs and governed MEASURE definitions using
  GRAPH_EXPAND, AGG(), and ISO GQL MATCH from Knowledge Catalog graph context.
  ALWAYS load FIRST (before execute_sql or execute_sql_readonly) on EVERY
  question when a BigQuery Property Graph or graphSchema is present.
---

Five elements inside the skill carry the accuracy and governance gain:

  1. Three symbolic SQL templates: One single-branch GRAPH_EXPAND rollup over Child (for ancestor AGG() deduplication and outer window shares), one multi-branch WITH CTE template that joins BranchA and BranchB onto Entity with COALESCE for empty sums and NULLIF for 0/0 ratios, and one standalone top-level GRAPH ... MATCH ... RETURN query (to prevent invalid SELECT ... FROM GRAPH_TABLE(...) wrappers).
  2. Standalone SELECT * prohibition: Placing the ban on SELECT * FROM GRAPH_EXPAND(...) on its own numbered line alongside the constructive alternative (SELECT DISTINCT Node_dim FROM GRAPH_EXPAND(...)) stops the model from probing schemas and hitting compile-time HTTP 400 MEASURE errors.
  3. Explicit synonyms and ancestor AGG() binding: Directing the model to match synonyms and description from Knowledge Catalog (including calling ancestor measures like AGG(Parent_cnt) directly when expanding Child and grouping by Child_dim) keeps it on governed measures instead of recomputing raw counts or placing CASE WHEN inside AGG().
  4. Catalog table guardrail: Treating BigQuery Table entries inside relatedResources strictly as sampleValues metadata prevents the agent from bypassing the graph and querying raw base tables.
  5. Zero-query abstention: Instructing zero SQL calls when a requested time axis or dimension is absent in the graph stops cross-dataset fishing and finishes abstentions in ~5 seconds.

Benchmark results#

We evaluated the live deployed ADK 2 agent (gemini-4-hydrogen, LOW thinking, compact symbolic skill) sequentially across all 20 isolated sessions on a warm runtime on Agent Runtime on Gemini Enterprise Agent Platform (us-central1), collecting OpenTelemetry traces for all 20 runs and scoring accuracy, groundedness, and strict SKILL.md SQL governance with gemini-4-neon (HIGH thinking):

All 20 questions (B01 through B10 and T01 through T10) returned the exact expected answer with zero SQL errors, zero raw-table leaks, and zero dry-run overhead. Seventeen of the 19 SQL-backed questions finished in a single SQL query (including the 6-metric B10 scorecard in 18.2s), B03 and T07 ran 2 clean queries, and T04 abstained in 5.5s with zero SQL calls. Because nearly every question finishes on its first SQL call, mean token usage stays tightly clustered at 27.3K (versus ballooning on retry loops), while Gemini’s implicit prefix cache still served 32.2% of prompt tokens across isolated Turn-1 sessions and compounds further across follow-up turns in the same session.

Tradeoffs#

Three operational boundaries are worth planning around when you run this pattern:

  1. Large-warehouse catalog hydration: Injecting one :lookupContext payload works cleanly for a single domain graph (4 nodes, ~8K tokens). On an enterprise warehouse with dozens of graphs and hundreds of tables, replace full-dataset Turn-1 hydration with per-question :searchEntries discovery so the prompt stays bounded.
  2. Agent Runtime GOOGLE_CLOUD_PROJECT vs BigQueryToolset: Inside Agent Runtime, GOOGLE_CLOUD_PROJECT is injected as the numeric project number rather than the string project ID returned in Knowledge Catalog graph URIs. Passing a separate string BQ_PROJECT_ID env var into BigQueryToolConfig(compute_project_id=BQ_PROJECT_ID, default_project_id=BQ_PROJECT_ID) avoids project-mismatch tool rejections.
  3. ADK 2 tool_filter interaction with adk_additional_tools: SkillToolset.get_tools() applies tool_filter across both built-in skill tools and dynamically activated additional_tools. Include each gated tool name in tool_filter (["load_skill", "execute_sql"]), or ADK will keep filtering out execute_sql after load_skill succeeds.

Putting the semantic contract in BigQuery Graph, hydrating its metadata once through Knowledge Catalog, and scoping BigQuery execution behind a compact symbolic skill lets gemini-4-hydrogen at LOW thinking serve governed analytics reliably in a single shot.
